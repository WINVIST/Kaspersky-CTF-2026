# RUSTyapa

**Категория:** Pwn  
**Стоимость:** 280

> Blazingly fast, memory safe, and fearlessly concurrent... Guess which statement is a lie.

В задании дали небольшую БД на безопасном Rust. В исходниках не было ни `unsafe`, ни FFI, а у бинаря были PIE, NX и full RELRO. Главной подсказкой оказался Dockerfile: программа собиралась строго на Rust 1.96.1.

## Разбор

Для этой версии компилятора есть баг кодогенерации [rust-lang/rust#159035](https://github.com/rust-lang/rust/issues/159035), исправленный в 1.97.1. Из-за него safe-код при определённой форме closure неправильно освобождает значения.

Подходящее место было в `run_batch`:

```rust
transaction(|mut tx| {
    tx.select(src).adjust(-amount).write(b"batch-out");
    tx.commit(db);
});
transaction(|mut tx| {
    tx.select(dst).adjust(amount).write(b"batch-in");
    tx.commit(db);
});
```

Если в первой транзакции выбрать несуществующую строку, а во второй нормальную, первый `commit` выйдет раньше времени, а второй успешно допишет теги. Триггер получился таким:

```text
3  # Transactions
3  # Batch transfer
3  # source row, не существует
0  # dest row
-1
```

После этого следующий короткий ввод обычно заканчивался `double free detected in tcache 2`. Под gdb оказалось, что в tcache для chunk размера `0x20` остаются три ссылки на один и тот же chunk `B`.

Вторая транзакция заодно расширяет `tags` у строки 0. Освобождённый payload переиспользуется, поэтому просмотр строки выдавал примерно такое:

```text
tags  : seed<8 bytes><1 byte>batch-in
```

Первые восемь байт между `seed` и последним байтом — safe-linked указатель chunk на самого себя:

```python
encoded = B ^ (B >> 12)
```

Обратное преобразование делается несколькими `xor` со сдвигом. Здесь появился неприятный нюанс: теги выводятся через `String::from_utf8_lossy`, поэтому невалидные байты превращаются в `ef bf bd`. Я просто переподключался, пока адрес и будущий tcache poison целиком не оказывались валидным UTF-8. Это происходит не на каждом запуске, поэтому в solve используется несколько параллельных соединений.

После бага цепочка выглядит как `B -> B -> B`. Имя строки длиной 16 байт дважды получает `B`, перезаписывает его `next` и один раз возвращает chunk в tcache. Следующее короткое имя уже выделяется по выбранному адресу.

Первой такой записью я задел соседние поля строки 0:

```text
name.len      = 0x4000
tags.capacity = 0x4141414141414141
```

Двоичные нули и ASCII остаются валидным UTF-8, поэтому ограничение `read_line` здесь не мешает. После этого `View row` отдаёт 0x4000 байт кучи, а `Deposit` считает, что у `tags` огромная capacity, и пишет note дальше настоящего буфера.

Перед tcache poison я создавал строку с именем длиной `0x500`, а потом удалял её. В heap dump оставались указатели unsorted bin. Из первого вычислялась база libc:

```python
libc = leaked_arena - 0x234c20
```

Во время двух вставок `Vec<Record>` переносится в новый chunk. Его адрес я не хардкодил, а искал в дампе по полному содержимому первой записи: указатель на `genesis`, длина имени, указатель на tags, `id` и `value`.

Сначала я заполнил всё расстояние от tags до нового массива буквами `X`. Это сразу ломало заголовки chunk. В рабочем варианте префикс копируется из полученного heap dump, а меняется только последний `Record`. Байты `0x0a` в префиксе заменяются, потому что note читается до первого переноса строки.

После первого длинного overflow я перенастроил `tags.ptr` так, чтобы следующий append снова начинался прямо с `Record`. Дальше для записи структуры было достаточно 64 байт. Поля имени стали примитивом чтения, а поля tags — примитивом следующей записи:

```text
name.ptr / name.len -> arbitrary read
tags.ptr / tags.len -> адрес следующего append
```

Сначала через `libc.environ` утёк адрес стека. Потом я поставил `name.ptr = environ - 0x10000` и прочитал окно размером 0x10000 байт. Активный return address `Transaction::commit` стабильно находился по адресу `environ - 0x3d0`.

Первая версия ROP просто писала цепочку начиная с return address. Она падала с `free(): invalid pointer`: qword сразу после RIP одновременно был полем `Transaction`, и деструктор пытался освободить адрес `/bin/sh` ещё до возврата из функции.

В итоге настоящую цепочку я положил в следующий heap `Record`, а на стеке перезаписал только сохранённые регистры и RIP. В saved `rbp` записал адрес heap-цепочки, в RIP — `leave; ret` из libc:

```text
leave; ret
pop rdi; ret
"/bin/sh"
ret
system
```

Так деструктор успевает нормально закончить работу, `commit` возвращается и делает stack pivot. Команду для shell пришлось отправлять отдельным пакетом уже после срабатывания ROP. Если послать её вместе с последним пунктом меню, Rust успевает забрать строку в свой stdin buffer, и `/bin/sh` её не увидит.

Полный эксплойт находится в [solve.py](solve.py). Он использует только стандартную библиотеку Python; несколько сотен или тысяч переподключений из-за условия на UTF-8 — нормальное поведение.
